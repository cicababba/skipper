**Critic 0.500** — verdict: concerns
- [wrong-approach] (blocking) Step 3 and Step 4 directly contradict each other on the delete rollback, and one of the two readings loses the user's data. Step 4 fixes the handler as `onDelete: (id: string) => void` wrapped in `useCallback` with an *empty* dependency list; Step 3 then says to restore the removed todo by capturing "the todo and its index ... from the current `todos` array before the call". Under empty deps that closure reads the mount-time `todos` — `[]` — so `findIndex` returns -1 and there is no `Todo` object in scope to re-insert at all (the handler only receives a primitive `id`). A failed DELETE would therefore drop the row permanently until reload, violating the acceptance criterion "the todo reappears (in its original position) with an error message if the DELETE fails". Adding `todos` to the dep array fixes the read but makes `onDelete` a new reference on every list change, which silently defeats the `memo` on every row — the plan's own risk #3. Only two paths actually work and the plan must name one: capture `todo`+index inside the functional `setTodos` updater (idempotent, so safe despite StrictMode double-invoking updaters — `main.tsx:10`), or widen the handler signature to `(todo: Todo)` and pass the object from `TodoItem`. Offering both options as interchangeable is what makes this blocking.
- [risk] The success-path reconcile (`replaceTodo(prev, updated)` after `await updateTodo`) reintroduces exactly the staleness the optimistic update is meant to remove, and the plan specifies no in-flight tracking. Two rapid toggles on the same row produce two in-flight PATCHes; whichever resolves last wins, so a slow first response overwrites the newer optimistic value and the checkbox visibly flips back under the user's finger. For a `done` toggle the server response carries nothing the client doesn't already know — `store.update` (`apps/api/src/store.ts:46-56`) just merges the field back — so the reconcile buys no information, costs a second re-render of that row, and creates the race. Either drop the reconcile for toggles or guard it with a per-id request sequence/latest-wins check.
- [risk] `setTodoDone(prev, id, !done)` is not a rollback, it is a recomputation. It writes the negation of the value that was *attempted*, which equals the value the row actually had only if nothing else wrote that todo in between. With overlapping toggles, or a toggle whose reconcile landed first, a failure writes a state the user never had and the UI drifts from the server — the precise failure mode listed as risk #1 but not actually prevented. Capturing the previous `done` value (or the previous `Todo`) at the start of the action is strictly simpler than reasoning about when the identity holds, and it makes toggle and delete rollback use the same shape.
- [wrong-approach] The memoization half of the plan is asserted, not measured. The verified cause of the reported symptom — "ticking one off takes a moment before anything happens on screen" — is entirely the `await updateTodo(...)` at `App.tsx:36`, which Step 3 alone fixes. The claim that per-row re-render is "the second half of the slowness" has no baseline behind it: each row is a plain `<li>` with a checkbox, a span and a button (`App.tsx:66-74`), and re-rendering a few hundred of those is a low-single-digit-millisecond job, well below the perceptual threshold. Worse, the prescribed verification ("Record a React DevTools Profiler pass") runs under `StrictMode` (`main.tsx:10`), which double-invokes renders in development, so the manual check measures an inflated dev-only cost and cannot confirm a real-world win. Recommend landing the optimistic update, measuring with the ~200-todo fixture the plan already describes, and treating `TodoItem`/`memo`/`useCallback` as conditional on that measurement — otherwise this is added indirection plus a new module boundary defended by nothing.
- [acceptance-gap] Acceptance criterion 4 ("Interacting with one todo no longer re-renders every other row") has no automated verification and cannot get one under the plan's own constraints: `vitest.config.ts:5` includes only `.ts`, and jsdom/@testing-library are explicitly out of scope, so the pure helpers in `todos.test.ts` can assert array identity but can never observe a render count.
